# Bug audit — 2026-07-07

Read-only audit of `lib/`, `app/api/`, `hermes/scripts/`, `scripts/`, and the in-scope
components. Each finding below has a concrete triggering sequence and was re-read against
the source before inclusion. Line numbers are as of this commit.

---

## HIGH

### [SEV: high] hermes/scripts/telegram_approval_bridge.py:257 — state file writes are not atomic; a crash mid-write wipes the entire bridge memory
`save_state()` does `path.write_text(...)` (truncate-then-write, no temp+rename). It is
called mid-loop before each send (line 556) and again at tick end (line 974), so the write
window is hit often. If the process is killed mid-write (launchd stop, OOM, power loss), the
JSON is left truncated; `load_state()` (line 250) catches the `JSONDecodeError` and silently
resets to `default_state()`. Effect on the next tick: `sent` is empty → **every** still-pending
draft is re-sent (duplicate Telegram messages); `msgIndex` is empty → real replies to older
drafts get "I don't recognise that draft"; `updateCursor` is lost → getUpdates re-delivers
already-processed updates (server 409→noop absorbs the decisions, but acks re-fire).
Fix: write to a sibling temp file in the same directory and `os.replace()` onto the target
(atomic rename), so a partial write can never be observed.

### [SEV: high] lib/publisher.ts:39-48 — Typefully draft is created before the Notion "Typefully ID" write, so a failed write duplicates the scheduled post
`scheduleOne()` calls `createScheduledDraft()` (line 39) and only then `updatePage()` to store
`Typefully ID` + set Queued (line 44). The module's idempotency ("items that already carry a
Typefully ID are skipped", runPublisher line 74) depends entirely on that ID being persisted.
If `updatePage` throws (429 after retries, transient Notion 5xx) after the draft was created,
the item stays `Approved` with no `Typefully ID`; the next cron run (or a user retry of
publish-next) creates a **second** Typefully draft → the post is scheduled/published twice.
Fix: after a Typefully failure this is safe, but a post-create Notion failure needs
reconciliation — e.g. look up the just-created draft by a deterministic client marker before
re-creating, or record the Typefully ID to Notion with its own retry before treating the slot
as unfilled.

### [SEV: high] lib/actions.ts:115-134 — editItem changes the body before persisting the "Original Draft" snapshot; a failure between them loses the true original
For X/LinkedIn (block-body) items, `editItem` calls `writeBody(pageId, newText)` (line 132)
**before** `updatePage(pageId, updates)` (line 134), where `updates` carries `Original Draft`
(the pre-edit snapshot) and `Edited Before Approval`. If `updatePage` throws after `writeBody`
succeeded, the page body is already the new text but `Original Draft` was never saved. A
subsequent edit reads `Original Draft` as empty (line 125) and snapshots the *already-edited*
body as the "original" → the genuine pre-edit text is permanently lost, and the approve-time
diff (actions.ts:79) is wrong. Also unlike `approveItem`, `editItem` has no pre-migration
fallback: on a DB lacking `Original Draft`/`Edited Before Approval`, `updatePage` throws
`SCHEMA_MISMATCH`-style errors *after* the body was already mutated. Fix: for block bodies,
compute and write the snapshot/flags first (or in the same write), then change the body last;
add the same `/Approved At|not a property/` fallback approveItem has.

## MEDIUM

### [SEV: medium] lib/notion.ts:225 & lib/items.ts:181 — block-body paragraphs over 2000 chars are silently truncated instead of chunked
`writeBody` builds each paragraph block as a single rich_text item with `content: p.slice(0, 2000)`;
`paragraphBlocksForCreate` (createDraft path) does the same. `richTextValue()` (notion.ts:175)
correctly chunks at 2000, and is used for property-stored bodies (IG) — but the block path does
not. A single paragraph with no blank-line break longer than 2000 chars (a wall-of-text LinkedIn
post, allowed up to ~3000 chars) loses everything past 2000 with no error; `readBody` and the
eventual Typefully publish only ever see the truncated text. Fix: split each paragraph's text
into multiple rich_text items (≤2000 each) within one paragraph block, mirroring richTextValue.

### [SEV: medium] hermes/scripts/sync_command_center_calibration.py:565 — the `since` watermark is the response `generatedAt`, so events created during the request window are skipped forever
After a run, state stores `since = data["generatedAt"]` (line 565); the next run queries
`?since=<that>` and filters `createdAt >= since_used` (line 546). But the server sets
`generatedAt = new Date()` *after* it has already snapshotted the CalibrationEvents list (and run
several more Notion calls). Any event created in the gap between that snapshot and `generatedAt`
has a `createdAt < generatedAt`, so it is absent from this response *and* excluded from the next
run's `on_or_after generatedAt` window → it never appears in any daily report. Single-user
volume makes it rare, but it is silent report loss. Fix: watermark from the max `createdAt`
actually returned (or `since` minus a small overlap), and dedupe by event `id` across runs.

### [SEV: medium] telegram_approval_bridge.py:955-974 & sync_command_center_calibration.py:522-566 — `--fixture` without `--dry-run` executes real sends/POSTs/writes against production
`--fixture` only short-circuits the *read* side (drafts/updates come from the file). If `--dry-run`
is omitted, the *write* side runs for real: the telegram worker sends actual Telegram messages
(if `TELEGRAM_BOT_TOKEN` set), POSTs real decisions to the Command Center (if `HERMES_API_TOKEN`
set), and calls `save_state()` on the real state file — advancing `updateCursor` to fixture ids
and injecting fixture retries. The sync worker writes a report into the real
`inbox/calibration/` and sets `state.since` to the *fixture's* `generatedAt` (a fake/old/future
date), which then corrupts the next real run's window (over-report, or silent skip if the fixture
date is in the future). The docstrings say fixtures are "test-only" but nothing enforces the
`--dry-run` pairing. Fix: make `--fixture` imply no network writes and no state persistence
(or hard-error if `--fixture` is given without `--dry-run`).

### [SEV: medium] scripts/export-twin-context.ts:656-666 — the backup's try/catch swallows `cp` failures as "file didn't exist", overwriting a canonical file with no backup
The pre-write backup loop does `await stat(dest)` then `await cp(dest, backup)` inside one `try`,
with a `catch` commented "File doesn't exist yet — nothing to back up." But the catch also
swallows a *failed cp of an existing file* (permissions, disk full, transient FS error). When
that happens `backedUp` is not incremented and the run proceeds to the write loop (line 672),
overwriting the original — the hand-curated `soul.md`/`constitution.md` — with the raw mechanical
mirror and **no backup**. Since protecting those canonical files is the entire reason the backup
exists, this is a real loss window. Fix: only treat `ENOENT` from `stat` as "nothing to back up";
if the file exists but `cp` fails, abort the whole write rather than overwrite unbacked.

### [SEV: medium] scripts/verify-draft-bridge.ts:94-135 — no try/finally cleanup; a mid-run throw orphans a test Draft in the live X content DB
The script creates a real Draft page (line 94) and archives it only at line 135, with nothing
between guarded. If any call in between throws (e.g. `getPage`/`readBody` hitting a transient
Notion error), control jumps to the top-level `main().catch` → `process.exit(1)` and the page is
never archived. Because this page is a `Status: Draft` X item, it then shows up in the real
approval queue *and* in `GET /api/hermes/drafts` / the export `pendingReview` count. Contrast
`verify-telegram-decisions.ts`, which correctly wraps cleanup in `try/finally`.
`verify-proposals.ts` (line 91→127) and `verify-calibration-events.ts` (line 45→81) share the
same unguarded pattern but write to log DBs (lower harm). Fix: wrap the body in `try/finally`
and archive every created id in the `finally`, matching verify-telegram-decisions.

### [SEV: medium] lib/actions.ts:75,101,156 — an awaited Pipeline Events write after the status change can 500 a fully-applied action and lose the KPI event
In `approveItem`/`rejectItem`/`markPostedItem`, `logEvent()` is awaited *after* the
status-changing `updatePage`, and is not wrapped. `logEvent` throws when `DS_EVENTS` is set but
the Notion POST fails (unlike `logCalibrationEvent`, which never throws). So a transient failure
writing the Pipeline Event surfaces as a 500 for an action whose status flip already committed;
the KPI event is dropped with no retry, and a user re-try hits the `!== "Draft"` guard → 409/confusing
error. Fix: make `logEvent` non-fatal on the action path (try/catch + warn, same discipline as
logCalibrationEvent), or log before the guard-relevant state is considered final.

## LOW

### [SEV: low] lib/route-helpers.ts:14 (and the per-route 500 handlers) — raw `err.message` is returned in 500 bodies, leaking internal Notion error text
`handleAction` and most route catch-blocks put `err.message` in the JSON response. `notionFetch`
embeds up to 500 chars of the Notion error body (property names, data source ids) in its thrown
message, so those reach the client. Behind single-user session auth the exposure is limited, but
it is needless internal leakage. Fix: return a generic message to the client, keep the detail in
`console.error`.

### [SEV: low] app/api/cron/publish/route.ts:11 & app/api/cron/reconcile/route.ts:11 — cron Bearer check uses `===`, not a constant-time compare
`auth === \`Bearer ${secret}\`` is a non-constant-time comparison of `CRON_SECRET`, inconsistent
with `lib/machine-auth.ts` which uses `timingSafeEqualStr`. Low practical risk, but trivially
alignable. Fix: reuse `timingSafeEqualStr`.

### [SEV: low] app/api/auth/login/route.ts:12-13 — login rate limit is keyed on the client-supplied `x-forwarded-for`, so it is bypassable
The limiter key is `x-forwarded-for.split(",")[0]`. A client can inject an `X-Forwarded-For`
header (Vercel appends rather than strips), so rotating fake values defeats the 10-attempt
window. The passphrase is sha256 + timing-safe, so this only weakens brute-force protection.
Fix: derive the client IP from the platform-trusted source, or fall back to a global limiter.

### [SEV: low] scripts/migrate.ts:158-168 (and 215, 302) — DB idempotency relies on Notion `/search`, which is eventually consistent
`ensureEventsDb`/`ensureCalibrationEventsDb`/`ensurePositionProposalsDb` decide "already exists"
via `/search`. Running `migrate` twice within Notion's search-index lag (seconds–minutes after a
create) would not find the just-created DB and would create a duplicate. It is a manual run-once
script so the odds are low, but the "idempotent" claim has this hole. Fix: prefer reading a known
data-source id from env when present, or re-verify by direct fetch before creating.

### [SEV: low] app/api/hermes/export/route.ts:66-73 — only the pipeline-events query is `.catch`-guarded; a Notion error in the other lanes 500s the whole export
`queryCalibrationEvents` and both `queryProposals` calls in the `Promise.all` are unguarded, so a
transient Notion error on a *configured* lane rejects the entire export (500), despite the doc's
"degrades gracefully" claim (which only actually holds for *unconfigured* env vars). Fix: give
each lane its own `.catch(() => default)` and surface a warning, matching the draft-count loop.

### [SEV: low] lib/notion.ts:52-69 — queryDataSource silently truncates at maxPages (default 5 → 500 rows)
`queryDataSource` stops after `maxPages` and returns what it has, with no signal. Status-filtered
content queries and KPI queries rely on it; for a single user the caps (500/1000 rows) are
unlikely to bite, but a lane exceeding them would drop rows silently (e.g. skewing KPI
drafts-produced or missing older Queued items in the reconciler). Fix: at minimum log when
`has_more` is still true at the cap.

## Fixes applied (2026-07-08)

Verified: `npx tsc --noEmit` clean; `py_compile` clean on both workers; both workers
hard-error (exit 5) on `--fixture` without `--dry-run` and still run under `--dry-run --fixture`.

### HIGH
1. **telegram_approval_bridge.py atomic state write** — `save_state()` now serialises to a
   sibling `.tmp.<pid>` file and `os.replace()`s it onto the target (atomic rename); a crash
   mid-write can no longer leave truncated JSON that resets all bridge memory.
2. **lib/publisher.ts scheduleOne duplicate-post window** — the `Typefully ID`/`Queued`
   `updatePage` is wrapped; on failure it `deleteDraft(draft.id)` to roll back the Typefully side,
   and if rollback also fails it logs a `Publish-failed` event whose notes carry the orphaned
   draft id, then rethrows. (Imports `deleteDraft`.)
3. **lib/actions.ts editItem ordering + fallback** — block-body path now persists the
   `Original Draft`/`Edited Before Approval` snapshot via `updatePage` BEFORE `writeBody`; the
   `bodyProp` path keeps body+snapshot in one `updatePage`. Both paths gained the pre-migration
   graceful fallback (retry body-only + `console.warn`) that `approveItem` has.

### MEDIUM
4. **lib/notion.ts writeBody & lib/items.ts paragraphBlocksForCreate** — each paragraph is now
   built with `richTextValue(p)`, chunking into multiple ≤2000-char rich_text items within one
   paragraph block instead of `p.slice(0,2000)`; no more silent truncation of >2000-char paragraphs.
5. **sync_command_center_calibration.py watermark + dedupe** — watermark is now the max `createdAt`
   across returned events (falls back to the previous watermark when none), and events are deduped
   across runs via a `seenIds` set (ids recorded at the watermark) persisted in the state file, so
   the query overlap never double-reports and gap-window events are no longer skipped.
6. **Both Python workers `--fixture` guard** — `--fixture` without `--dry-run` now hard-errors on
   stderr with new exit code 5 (documented in each file's exit-code table) before any send/POST/write.
7. **scripts/export-twin-context.ts backup safety** — the pre-write backup now treats ONLY `ENOENT`
   from `stat` as "nothing to back up"; any other stat/cp failure marks the file skipped (never
   overwritten unbacked), reports it to stderr + the summary line, and forces a non-zero exit.
8. **scripts/verify-draft-bridge.ts try/finally** — the created test page is now archived in a
   `finally` so a mid-run throw can't orphan a Status:Draft X page in the live queue. Same pattern
   applied to `verify-proposals.ts` and `verify-calibration-events.ts` (both also affected).
9. **lib/actions.ts non-fatal logEvent** — the `logEvent` calls after the status change in
   `approveItem`/`rejectItem`/`markPostedItem` are now `.catch`+`console.warn` (non-fatal), so a
   transient Pipeline Events failure no longer 500s an already-applied action. `logEvent` itself is
   unchanged (crons still use it).

### LOW
10. **cron publish/reconcile routes constant-time compare** — both `authorised()` checks now use
    `timingSafeEqualStr` (already exported from `lib/auth.ts`) for the `Bearer` and `x-cron-secret`
    secret comparisons instead of `===`.
11. **app/api/hermes/export/route.ts graceful lanes** — the calibration-events and both proposals
    queries in the `Promise.all` now each have a `.catch` → empty result + a `warnings` entry, so a
    transient Notion error on a configured lane no longer 500s the whole export.

- LOW: login rate limit keyed on client-supplied `x-forwarded-for` (app/api/auth/login/route.ts).
- LOW: `migrate` DB idempotency relies on eventually-consistent Notion `/search` (scripts/migrate.ts).
- LOW: `queryDataSource` silently truncates at `maxPages` cap (lib/notion.ts).
